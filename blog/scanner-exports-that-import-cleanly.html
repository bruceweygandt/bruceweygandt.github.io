Notes from making scanner exports import cleanly

Vulnerability management, SAST and DAST, ConMon. 2 min read.

What I found building intake presets for Fortify, Qualys, Grype, and SentinelOne.

During onboarding, clients were spending time reshaping scanner exports before we could use them. My job was to build File Intake Presets so they could upload whatever their tools already produce. Most of the work turned out to be learning where each format hides things.

How I worked

For every format, I parsed real sample files in Python before opening the preset wizard, so each field mapping was checked against actual data rather than documentation. Where no public sample existed, I generated synthetic fixtures so the preset could still be tested without anyone's real findings.

Fortify

I built four OpenText Fortify presets: SAST in XML, FPR, and CSV, and DAST in XML. Two things surprised me. The standard ReportGenerator XML only emits one issue per category, so it quietly undercounts unless you use the all-issues template. And Fortify CSV isn't a scanner output at all. It only exists downstream of Software Security Center, which flips the usual assumption that CSV is the easy option.

Qualys

In the Qualys API XML, the detection rows and the details that matter, like severity, title, and CVE, live in separate branches joined by an ID. A preset can't reach across that join, so I ruled the format out and built on an export that keeps everything on one row.

Grype and SentinelOne

Container and endpoint findings were the easier part. For Grype I went a step further and helped build a CI/CD pipeline that sends scan results to Paramify automatically, so nobody has to remember to upload them.

Informational findings

Every scanner reports some findings that aren't vulnerabilities. Those are filtered out or mapped to a tier with no remediation clock, so they don't inflate POA&M counts.
