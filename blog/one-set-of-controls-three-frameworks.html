One set of controls, three frameworks

NIST CSF 2.0, ISMAP, Framework mapping. 2 min read.

Mapping NIST CSF 2.0, Japan's ISMAP, and FedRAMP's new identifiers onto capabilities that already exist.

Most companies I work with answer to more than one framework. A cloud provider pursuing FedRAMP may also need NIST CSF 2.0 for commercial customers, and one selling to Japanese government agencies needs ISMAP. Writing the same implementation up three times is slow, and the copies drift apart.

My approach is to map every framework to the capabilities that are actually implemented, rather than framework to framework. Update one capability, and every framework that references it stays current.

Check the foundation first

Before mapping anything new, I checked whether the existing FedRAMP 20x Moderate capabilities really covered the controls they were mapped to. Mapping a new framework onto weak coverage just spreads the weakness. A short Python pass made the thin spots obvious.

NIST CSF 2.0

I mapped all 106 CSF 2.0 subcategories, 554 links in total. Where coverage was missing, I drafted six new capabilities. Where it was weak, I strengthened six existing ones instead of stretching them to fit.

ISMAP

ISMAP is Japan's security assessment program for government cloud services. I built a 1,298-row crosswalk from ISMAP to NIST 800-53 Rev 5, working from the Japanese source text. Translations of control language tend to lose exactly the qualifiers that matter in an assessment, so reading the original was worth the time.

FedRAMP's renaming

FedRAMP 20x moved KSIs from numbered identifiers to short mnemonic ones. I mapped the new IDs to the old so existing evidence and capabilities stayed connected through the change.
